01언제 — P9까지 끝내고 나서가 아니라 지금입니다

P4 직후인 지금이 가장 싼 시점입니다. 단, "새 에디터"가 아니라 "분해 + 미리보기 + 자동저장"입니다.

P5~P8은 전부 에디터에 패널을 하나씩 얹는 작업입니다 — 결제(활성화 버튼), 브랜드키트(로고 패널), 위젯(연결 버튼 패널), 문의함, 배너, 후기. 지금 691줄짜리 ui.tsx 한 파일에 그것들을 계속 붙이면 P8쯤엔 2,500줄이 되고, 그때 쪼개는 비용은 지금의 5배입니다. 클로드코드가 무거운 이유의 절반도 이 파일입니다.

반대로 "에디터를 통째로 새로 짓는 것"은 지금 하면 안 됩니다. 폼 기반 에디터는 폰에서 홈온의 캔버스보다 낫고, 이미 12섹션 편집·업로드·발행·점수·소유권이 프로덕션에서 검증됐습니다. 버릴 게 없습니다. 필요한 것은 구조(파일 분해)와 체감(즉시 미리보기·자동저장·되돌리기) 두 가지입니다.

현재 코드를 다시 읽으니 지난 리포트에서 "섹션 삭제 없음"이라 적은 것은 이미 해결돼 있었습니다 — ui.tsx의 deleteSection(hero·quoteForm 보호)과 goToAnchor(＋N점 클릭 스크롤)가 2026-09-02자로 들어가 있고, tours.ts도 현 화면에 맞게 재정의됐습니다. 남은 실제 격차는 미리보기 없음 · 자동저장 없음 · 되돌리기 없음 · 파일 1개에 전부 네 가지입니다.

02클로드코드가 무거운 이유와 처방

/clear를 해도 무거운 것은 대화 길이 문제가 아니라 세션을 시작할 때마다 자동으로 읽히는 양의 문제입니다. 현재 저장소에서 원인을 셋 찾았습니다.

원인현재처방
PROGRESS.md 673줄(67KB)CLAUDE.md가 "목록은 docs/PROGRESS.md"로 가리켜 매 세션 통째로 읽힘. 내용의 80%는 끝난 일의 기록(P3·P4 E2E 상세, Vertex 이관 경위, WIF 함정).docs/STATUS.md(≤60줄) 신설 — "지금 어디·다음 뭐·막힌 것"만. PROGRESS.md는 docs/archive/2026-09-progress.md로 이동. CLAUDE.md는 STATUS만 가리킴.
ui.tsx 691줄 단일 파일에디터를 한 글자 고쳐도 691줄을 읽고, 수정 diff도 큰 파일 기준으로 계산됨. ContentTab 안의 switch가 12섹션 폼을 전부 품음.05장 구조로 파일 20개로 분해. 이후 "hero 폼 고쳐줘"는 60줄짜리 파일 하나만 읽음.
CLAUDE.md의 "현재 상태" 절날짜·커밋·E2E 결과가 CLAUDE.md에 들어가 규칙 파일이 일지가 됨(54줄이지만 상태 절이 절반).CLAUDE.md는 규칙·스택·명령어만(30줄). 상태는 STATUS.md로.

세션 운영 규칙 5가지 (이걸로 체감이 반으로 줄어듭니다)

① 한 세션 = 한 작업 = 파일 목록 명시. 프롬프트 첫 줄에 "읽을 파일: A, B, C. 그 외는 읽지 마"를 씁니다. 클로드코드는 지시 없으면 탐색하면서 컨텍스트를 태웁니다. 07장 프롬프트는 전부 이 형식입니다.

② /clear 대신 /compact를 작업 중간에. clear는 다시 CLAUDE.md·STATUS를 읽게 만들고, compact는 지금까지의 결론만 남깁니다. 작업이 끝나면 그때 clear.

③ 서브에이전트로 읽기를 위임. "이 파일들을 읽고 요약만 돌려줘"는 Task(서브에이전트)로 시키면 본 세션에 원문이 안 들어옵니다. 프롬프트에 "탐색은 서브에이전트로, 본 세션에는 결론만"을 넣습니다.

④ 완료 조건을 먼저 쓰고 시작. "npm run build 통과 + 다음 4가지가 화면에서 확인되면 끝"을 프롬프트에 넣으면 에이전트가 검증 루프를 스스로 끝냅니다. 없으면 무한히 "확인해볼까요"를 반복합니다.

⑤ ultracode는 정합성 작업에만. CLAUDE.md의 게이트대로 스키마 4곳 동시 수정·새 라우트+컴포넌트 결합에만 쓰고, 단일 파일 분해·폼 하나 만들기는 일반 모드로. ultracode는 에이전트 7개를 띄우므로 무거움의 주범이 되기도 합니다.

03병렬 작업 — 다른 클로드코드 세션에서 따로 만들어 합칠 수 있나

가능하고, 권장합니다. 방법은 git worktree입니다. 같은 저장소를 폴더 두 개로 체크아웃해 각 폴더에서 클로드코드를 따로 띄우면, 세션마다 컨텍스트가 독립되고 브랜치도 분리됩니다. 별도 저장소를 만들 필요가 없고(모노레포 1개 결정 유지), 합치는 것은 PR 머지입니다.

# 본 저장소 옆에 작업 폴더 2개
cd C:\Users\ariancepc\Desktop\cowork\fable51plandept
git -C onstori worktree add ../onstori-wt-editor  -b editor-v2/shell
git -C onstori worktree add ../onstori-wt-preview -b editor-v2/preview

# 각 폴더에서 클로드코드를 따로 실행 (npm install은 각 폴더에서 1회)
cd onstori-wt-editor  && claude
cd onstori-wt-preview && claude

# 끝나면 각 브랜치를 main에 PR → 머지 → worktree 정리
git -C onstori worktree remove ../onstori-wt-editor

충돌 없이 나누는 원칙 — 파일 소유권 + 계약 우선

두 세션이 같은 파일을 만지면 머지에서 충돌합니다. 그래서 세션 0에서 계약(타입·파일명·postMessage 메시지)을 한 커밋으로 먼저 확정하고, 그 다음 세션들은 자기 소유 파일만 만집니다. 이 플랜의 분할은 다음과 같습니다.

A와 B는 파일이 겹치지 않으므로 동시에 두 창에서 돌릴 수 있습니다. C·D는 A의 결과 위에 얹히므로 순서대로. 세션 A가 가장 크지만(분해), 로직을 바꾸지 않는 이동 작업이라 리스크는 낮습니다.

나눌 수 없는 것 — lib/schema.ts는 항상 한 세션만. 두 세션이 동시에 스키마를 바꾸면 "4곳 동시 수정" 규칙이 깨집니다. 그래서 위젯(D)은 마지막에 단독으로 갑니다. DB 마이그레이션도 마찬가지로 한 번에 한 세션.

04홈온보다 빠르고 쉬운 에디터 — 설계

홈온 에디터(캡쳐 60여 장)의 실체는 "3단 캔버스처럼 보이는 폼 에디터"입니다. 중앙 캔버스는 클릭 선택만 되고 편집은 우측 폼에서 합니다. 사용자 불만은 "글자체·크기 못 바꿈", "저장 눌러야 함", "24시간 체험". 온스토리가 이길 지점은 캔버스를 흉내 내는 것이 아니라 폰에서 세 번 탭이면 고쳐지는 것입니다.

// lib/editor/preview-protocol.ts
import type { SiteDocT, StoryEntryT } from "@/lib/schema";

export type ToPreview =
  | { type: "onstori:doc"; doc: SiteDocT; stories: StoryEntryT[] }   // 에디터 → 미리보기: 다시 그려라
  | { type: "onstori:scroll"; idx: number };                           // 에디터 → 미리보기: idx 섹션으로 스크롤

export type FromPreview =
  | { type: "onstori:ready" }                                          // 미리보기 → 에디터: 로드됨, doc 보내라
  | { type: "onstori:focus"; idx: number };                            // 미리보기 → 에디터: 사용자가 idx 섹션을 탭했다

export const PREVIEW_ORIGIN = typeof window !== "undefined" ? window.location.origin : "";
export function isFromPreview(e: MessageEvent): e is MessageEvent<FromPreview> {
  return e.origin === PREVIEW_ORIGIN && typeof e.data?.type === "string" && e.data.type.startsWith("onstori:");
}

흐름: 에디터가 <iframe src="/{slug}/preview">를 띄움 → 미리보기 페이지는 서버에서 loadOwnedSite로 소유 검증 후 draft를 초기 렌더(첫 화면이 비지 않게) → 로드되면 ready 송신 → 에디터는 doc이 바뀔 때마다 300ms 디바운스로 doc 송신 → 미리보기는 useState(doc)를 갈아끼워 SiteRenderer 재렌더. 사용자가 미리보기 섹션을 탭하면 focus 송신 → 에디터가 해당 카드를 펼치고 scrollIntoView.

보안: 같은 오리진만 허용(e.origin 검사), 미리보기 라우트는 소유자·운영자만(403), robots: noindex, 발행본과 무관하므로 손님에게 노출되지 않습니다. draft 렌더는 zod SiteDoc.safeParse를 통과한 것만 그리고, 실패 시 마지막 정상 doc을 유지합니다(입력 중간 상태에서 화면이 깨지지 않게).

스토리는 draft 밖(즉시 공개)이므로 미리보기 초기 렌더 때 서버가 함께 넣어주고, 이후 doc 메시지에도 같은 배열을 동봉합니다.

하지 말 것

  • 자유 드래그 캔버스(GrapesJS·Puck·Craft.js류) 도입 — 폰에서 못 쓰고, 12섹션 스키마 구조와 충돌하며, 홈온도 결국 폼입니다.
  • 세션 A에서 "겸사겸사" 동작 개선 — 분해와 개선을 섞으면 회귀를 못 찾습니다. A는 이동만.

  • 미리보기를 iframe 새로고침으로 구현 — 저장 왕복이 생겨 "즉시"가 사라지고 서버 부하가 타이핑마다 납니다. postMessage가 정답입니다.
  • 홈온의 3단 캔버스·투어 문구·"+N점" 표기 방식 그대로 옮기기(CLAUDE.md 규칙 8).
