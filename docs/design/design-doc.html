리스크 & 선검증 — 먼저 읽기

투자자 관점의 비판적 분석 — 이 사업이 죽는다면 코드가 아니라 유통 때문이다

치명적 결함 후보 4가지

  1. 이 제품은 손님을 데려오지 않는다 (최대 결함). 사장님이 돈을 내는 이유는 홈페이지가 아니라 문의(리드)인데, 신규 서브도메인 사이트는 방문자 0에서 시작하고 네이버 검색에서 플레이스·블로그에 밀립니다. 시공 업종은 이미 숨고·집닥·오늘의집에서 리드를 돈 주고 삽니다 — "문의 1건 = 수백만 원"은 거꾸로 "리드 0인 홈페이지는 월 9,900원도 아깝다"로 작동합니다. 방문자 없는 3개월 = 해지. 홈ON의 두꺼운 전환 장치(카운트다운·혜택 배지)가 곧 "수요가 당기는 시장이 아니다"라는 방증.
  2. 핵심 차별화(스토리)가 사장님의 지속적 글쓰기에 베팅한다. 가장 바쁘고 디지털과 먼 직군이 매주 콘텐츠를 올려야 차별화가 성립. 소상공인 블로그의 현실은 "3주 뒤 방치". 스토리가 안 쌓이면 온스토리는 기능 적은 홈ON이 됨. UI로 마찰을 줄여도 이것은 행동 문제라 완전 해결 불가.
  3. 히어로 무비는 SaaS가 아니라 프리랜서 외주업. 199,000원 ÷ (재생성 API비 + 편집 3~6시간 + 수정 3회) = 시급 3~5만 원 이하 가능. 확장 = 인력 채용의 선형 비즈니스. 경쟁자는 크몽 영상 프리랜서와 매달 싸지는 AI 영상 툴 자체. "무비가 구독을 늘린다"도 미검증 가설 — 방문자가 0이면 무비가 있어도 해지함.
  4. 해자(moat)가 없다. 이 기획서가 경쟁사 하루 관찰로 나왔다는 사실 = 진입장벽 부재의 증명. 스토리 피드가 통하면 홈ON이 한 스프린트에 복제 가능. 위로는 아임웹·카페24·Wix/Canva AI가 가격을 무료 쪽으로 압박. 남는 해자 후보: 쌓인 스토리의 이전 비용(단, ②가 성립해야) + 무비 제작 노하우(단, ③ 참조).

그 외 무시 못 할 리스크

  • 1인 운영 부담: 개발+영상 제작+전화 영업+CS(밤 10시 카톡 "사진이 안 올라가요") 동시 수행 — 구독 100개 전 번아웃 위험.
  • LTV vs CAC: 자영업 폐업률 감안 시 LTV 12~20만 원 수준 — 전화 영업/광고 CAC가 이를 넘으면 성장할수록 손해.
  • 네이버 플레이스 불러오기: 약관·DB권 그레이존 — 네이버가 막으면 온보딩 편의성 하락.
  • 무료 10건 캠페인의 순서 모순: 런칭 시점 유료 고객 0명 → 첫 무비는 지인·베타에게 제공하는 것으로 수정.

살아남는 시나리오

벤처 스케일은 어렵지만 "인테리어 니치 + 전화 영업 + 제작 대행 하이브리드" 1인 사업으로는 성립 가능. 조건은 포지셔닝 수정: 파는 것을 "홈페이지"가 아니라 "견적 문의가 들어오는 상태"로 — 숨고 프로필·네이버 플레이스·홈페이지·시공사례 아카이브를 한 덩어리로 세팅해 주는 상품이면 결함 ①을 정면으로 다루게 됨.

선검증 3종 (코딩과 병행, 2~4주)

  1. 2주 선판매 테스트: 랜딩 1장 + 무비 샘플 1개 → 인테리어 사장님 30명 전화 → "49,000원+월 9,900원, 예약금 내시면 1호 제작" → 실제 결제가 나오는지 측정. 30명 중 2명 결제 = 청신호 / 0명 = 포지셔닝 재고.
  2. 컨시어지 MVP: 첫 5곳은 시스템 없이 수제작 지원 — 사장님들이 진짜 원하는 게 스토리인지, 무비인지, 네이버 상위노출인지 청취.
  3. 스토리 가설 검증: 베타 5곳에 "매주 사진 2장만 카톡으로 보내주세요, 올려드립니다" → 4주 지속률 측정. 지속 실패 시 "사장님이 쓴다" → "우리가 대신 써준다(대필 구독)"로 상품 전환 — 오히려 단가 인상 명분.
빌드 게이트 (공수 투입 규칙) P0~P1은 비용이 거의 없으므로(1인 공수 3주, 현금 ~2만원) 선검증과 병행한다. 단 P2(AI 생성·이미지 뱅크)와 P3(에디터) 진입 전에 선판매 테스트 결과를 확인한다 — 결제 의사 0이면 멈추고 포지셔닝을 다시 잡는다. "만들면 팔린다"는 가정에 4개월을 걸지 않는다.

  • 스토리 엔트리 = 날짜 + 제목 + 본문 + 사진 + 유형(작업기록 | 소식 | 이정표 | 손님이야기). 사장님이 카톡 보내듯 짧게 올리면 "우리 가게 이야기" 타임라인에 차곡차곡 쌓임. 시공 업종에서는 이것이 곧 시공 사례 아카이브가 됨 — 견적 문의를 부르는 최고의 영업 자산.
  • 실적 카운터 — "시공 사례 127건", "함께한 고객 3년차" 같은 숫자가 엔트리에서 자동 집계되어 히어로·소개 섹션에 표시.
  • 부가 효과 — 새 글이 계속 올라가는 사이트는 SEO에 유리하고, "이번 달 스토리 2건 작성 시 완성도 +10점" 넛지(5장)로 이어져 구독 유지 장치가 됨.
  • 생성 시 첫 스토리 — 위저드에서 "가게를 시작한 이유" 한 줄을 받아 AI가 첫 엔트리를 써서 심어줌.

3층 모델 — 이 구조가 좋은 이유

제안하신 구조는 사실상 3개 층의 분리이고, 이는 홈ON의 평면적 업종 목록보다 우수합니다:

업종(무한)  →  카테고리 7 (내부 분류·마케팅용)  →  템플릿 5 (화면 구조·CTA)
"도배·장판"      5. 시공·출장                        QUOTE (견적 문의)

검토에서 짚은 4가지 (구조는 승인, 디테일 보완)

  1. 카테고리 4의 병원·의원 — 의료법 주의. 의료광고는 환자 치료경험담·후기 광고가 금지되고 사전심의 대상이 될 수 있습니다. v1 enum에 없으므로 당장 문제없지만, 추후 도입 시 의료 업종은 후기 섹션 자동 비활성화 + 의료광고 심의 안내 문구를 정책으로 예약해 둡니다(13장에 반영).
  2. 카테고리 6 "날짜 예약"의 범위. 실시간 빈자리 캘린더는 무거운 기능입니다. BOOK 템플릿 v1은 희망 날짜를 적어 내는 "예약 신청 폼"(사장님이 확인 후 확정)으로 정의 — 홈ON의 예약 접수도 이 방식입니다. 실시간 슬롯 예약은 백로그.
  3. 카테고리 3의 CTA "상담·체험신청". CONSULT 템플릿에 폼 제목·필드만 바꾼 "체험신청 변형"으로 커버 — 템플릿을 6개로 늘리지 않습니다.
  4. 경계 업종(꽃집=방문+주문, 공방=판매+클래스). 추론은 주 수익 활동 기준으로 하고, 에디터에서 템플릿 전환 가능하게 설계해 흡수합니다(전환 시 전용 블록만 교체, 공통 블록·스토리는 유지).

온보딩 설계 — 카테고리를 묻지 않는 위저드

"묻지 않아도 아무 문제 없음"을 성립시키는 추론 파이프라인 — 0단계 설계의 핵심

위저드 화면 흐름 (질문 최소화)

onstori.com/new
① 상호명            "니브인테리어"                       [필수 · 텍스트 1칸]
② 하는 일 한 줄     "주거 인테리어 리모델링을 해요"       [필수 · 자유 문장]
   └ (선택) 네이버 플레이스 불러오기 → 주소·전화·소개 자동 채움
③ 주소(슬러그)      onstori.com/niv   [실시간 중복·예약어 검사 · 추천 3개 제시]
④ 분위기            [깔끔] [따뜻] [프리미엄] [활기]      [카드 4개 · 탭 1번]
⑤ 시작한 이유 한 줄  "아버지 밑에서 10년 배우고 독립했어요" [선택 · 첫 스토리 재료]
→ 생성 (진행률 화면) → 완성본 미리보기

사용자가 하는 일: 타이핑 3번 + 탭 2번. 카테고리도, 템플릿도, 업종 카드도 묻지 않습니다.

뒤에서 도는 추론 파이프라인 (이것이 "없어도 문제 없음"의 근거)

  1. 1차 — 키워드 사전 매칭 (0원, 즉시): industries.ts의 업종별 키워드 사전("인테리어·리모델링·도배·장판·타일…" → cat5/QUOTE)과 ②번 문장을 대조. v1은 14업종이라 사전만으로 대부분 적중.
  2. 2차 — LLM 분류 (사전 미적중 시): ①+②+플레이스 소개글을 Gemini(Vertex 경유)에 넘겨 {industry, category, template, cta_type, confidence} JSON으로 분류. 카피 생성 호출에 얹으면 추가 비용 ~0원.
  3. 3차 — 확신 낮을 때만 되묻기: confidence 낮음 → 생성 직전에 딱 한 번 "혹시 이 중 어디에 가까운가요?" 카드 2~3개 제시(전체 7개를 보여주지 않음). 높으면 그냥 진행.
  4. 4차 — 에디터에서 교정 가능: 추론이 틀렸어도 에디터 설정에서 템플릿 전환 1번이면 복구. 추론 결과와 사용자 교정 여부를 로깅해 키워드 사전을 계속 보강.
왜 이 설계가 옳은가 카테고리는 우리의 내부 어휘지 사장님의 어휘가 아닙니다. "당신은 예약·케어인가요 전문가·상담인가요"는 사장님에게 시험 문제일 뿐입니다. 사장님은 자기 일을 자기 말로 쓰고, 분류는 시스템의 일 — 이것이 홈ON의 11단계 대비 명확한 UX 우위가 됩니다.

게이미피케이션 · 가이드 투어 기반 설계

애니메이션·툴팁 UI는 나중에 입혀도, 데이터 구조와 DOM 뼈대는 P1부터 — 요청하신 그대로

목표 퍼널

신입 가입자가 혼자서 생성 → 첫 수정 → 발행 → 결제까지 완주하는 것. 이 4개 관문을 데이터로 추적하고, 완성도 점수와 투어가 다음 관문으로 밀어주는 구조입니다.

① 완성도 점수 — 규칙표가 곧 데이터 구조

주소 아키텍처 — 경로 방식 (2026-09-01 전면 전환)

onstori.com/{slug} — 서브도메인을 버린 결정적 이유는 네이버다
전환 사유 (핵심) 네이버 서치어드바이저는 사이트를 하나씩 등록하고 소유 확인(HTML 태그)을 해야 하며, 캡차로 프로그램 자동 등록을 차단한다. 서브도메인 방식이면 고객 1,000명 = 등록 1,000번 = 캡차 1,000번 + 사이트맵 1,000회 제출 + 신규 도메인 수집 ~2주 대기. 경로 방식이면 도메인 1회 등록 + 통합 사이트맵 1개로 전 고객 자동 커버이고, 신규 고객 사이트는 크롤러가 매일 오는 도메인에 페이지 하나 추가일 뿐이라 빠르게 잡힌다. 신규 서브도메인은 권위 0에서 시작하지만 경로는 도메인 신뢰를 승계한다 — 홈ON이 경로형인 진짜 이유.

섹션 JSON 스키마 입문 — 배우면서 만들기

스키마·zod·렌더러가 무엇이고 왜 한 몸인지

① 섹션 JSON — 홈페이지를 데이터로 표현

{
  "schemaVersion": 1,
  "template": "quote",
  "theme": { "palette": "clean", "accent": "#2B5BD7", "font": "pretendard" },
  "sections": [
    { "type": "hero", "headline": "10년의 현장이 말합니다",
      "sub": "주거 인테리어 리모델링 · 니브인테리어",
      "image": "bank/construction/clean/hero-02.webp",
      "cta": { "label": "견적 문의", "action": "quote" } },
    { "type": "portfolioGallery", "title": "시공 사례", "fromStory": true },
    { "type": "processSteps", "steps": ["상담","실측","시공","AS"] },
    { "type": "quoteForm", "allowPhotos": true },
    { "type": "storyFeed", "title": "니브의 이야기", "showCount": 5 },
    { "type": "map", "address": "…" }
  ]
}

모든 섹션은 type을 갖고, type마다 들어갈 속성이 정해져 있습니다. 이 약속이 스키마입니다.

② zod — 약속을 코드로 강제하는 검사기

const QuoteForm = z.object({
  type: z.literal("quoteForm"),
  title: z.string().default("견적 문의"),
  allowPhotos: z.boolean().default(true),
});
export const Section = z.discriminatedUnion("type",
  [Hero, StoryFeed, PortfolioGallery, ProcessSteps, QuoteForm, Gallery, Map /*…*/]);
export const SiteDoc = z.object({
  schemaVersion: z.literal(1),
  template: z.enum(["visit","book","quote","consult","browse"]),
  theme: ThemeSchema,
  sections: z.array(Section).min(1),
});
export type SiteDocT = z.infer<typeof SiteDoc>;   // TS 타입 자동 생성

AI는 가끔 약속을 어긴 JSON을 뱉으므로, 검사 지점 3곳에서 zod가 막습니다: ① AI 생성 결과 ② 에디터 저장 ③ 렌더러 읽기(안전망).

③ 렌더러 — JSON을 화면으로

const registry = { hero: HeroSection, storyFeed: StoryFeedSection,
  portfolioGallery: PortfolioSection, processSteps: ProcessSection,
  quoteForm: QuoteFormSection, gallery: GallerySection, map: MapSection };

// app/_sites/[slug]/page.tsx — 핵심은 이게 전부
const doc = SiteDoc.parse(site.published);
return doc.sections.map((s, i) => {
  const Comp = registry[s.type];
  return <Comp key={i} {...s} theme={doc.theme} />;
});

④ 왜 "한 커밋에서 같이"인가

스키마 문서(SCHEMA.md)·zod·렌더러·에디터 폼은 같은 약속의 네 표현입니다. 하나만 고치면 어긋남이 쌓이고, 그게 "프로젝트가 꼬인다"의 정체. 규칙: 섹션 변경 = 4곳을 함께 고치는 하나의 커밋. Claude Code에게도 그렇게 시키면 됩니다.

⑤ 버전 마이그레이션

schemaVersion 필드 + 렌더러 입구의 변환 함수(migrateV1toV2)로 오래된 사이트도 안 깨지게.

"만들면서 배워도 될까?" — 네, 그게 정석 P1 첫날 "hero·gallery·map 3섹션 최소 스키마+렌더러를 주석 달아 만들어줘"로 시작하면 반나절에 감이 옵니다. 당신의 역할은 코드가 아니라 약속이 바뀔 때 4곳이 같이 바뀌었는지 확인입니다.

법 · 라이선스 · AI 고지 정책

  • 별점·평점 입력 기능 자체를 만들지 않음. 실제 후기+출처 필드만. 대가성 후기 "협찬" 표기 안내.
  • 실적 카운터는 story_entries 실데이터 집계만 — 임의 숫자 입력 불가(컨셉과 일치).
  • 무비 광고 문구는 2장의 "수작업 표현 가이드" 준수.
  • 의료 업종 예약 정책(카테고리 4 확장 시): 의료광고는 환자 치료경험담 광고 금지·사전심의 이슈 → 의료 업종 감지 시 후기 섹션 자동 비활성화 + 안내 문구. v1 enum에 없어 당장 해당 없음.
