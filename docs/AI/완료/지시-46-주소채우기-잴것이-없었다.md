# 지시 [46] — 「주소 없는 기록 채우기」 · **채울 것이 0건이었습니다**

날짜: 2026-09-18 · 요청: 권반장 · 상태: **조사 완료 · 코드 변경 없음**

## 0. 결론

| 시킨 것 | 결과 |
|---|---|
| ① `remote_post_id` 로 다시 물어 `remote_url` 채우기 | ❌ **채울 것이 없습니다**(아래 §1) |
| ② 저장해 두고 쓰기(매번 안 물어보기) | — 채울 것이 없어 해당 없음 |
| ③ 옛 기록도 한 번 채우기 | ❌ **0건** |
| ④ 틱톡은 주소를 안 준다 — 정상 | ✅ **맞습니다.** 확인했습니다 |
| ⑤ ♡·💬 숫자도 같이 오나 | ✅ **옵니다.** 실측했습니다(§3) |

**코드는 한 줄도 안 바꿨습니다.** 대신 **[48] 의 판정이 옳았다는 것을 «훨씬 센 증거»로 확인**했고,
**지금 손님 화면에 죽은 링크 2개가 걸려 있다는 것**을 찾았습니다(§4).

## 1. 「주소 없는 published 2건」의 정체 — 둘 다 채울 수 없는 것이었습니다

`sns_posts` 전체 15건 · `published` 4건. 그중 주소 없는 것 2건:

| | 무엇 | 채울 수 있나 |
|---|---|---|
| 1 | **틱톡** `v_pub_file~v2-1.7686…` | ❌ **틱톡은 애초에 주소를 안 줍니다** — 권반장님 ④ 그대로. **없는 것이 정상** |
| 2 | **인스타** `18095011289101521` · **이미 «지워짐»으로 표시된 것** | ❌ **그 글이 존재하지 않습니다.** 물어볼 대상이 없습니다 |

⇒ **①③ 의 대상이 0건입니다.** 0건짜리 채우기 장치를 만드는 것은
`CLAUDE.md` §2-0 의 「안 만들어도 되는 셋」 중 **①정말 불필요**라 **안 만들었습니다.**

★ 그리고 **새 글은 이미 주소가 저장됩니다** — 발행 직후 `fields=permalink` 로 받아 적습니다
  (`lib/sns/instagram.ts:306`). 최근 2건 모두 주소가 들어 있습니다.

## 2. 🔴 확인하다가 «[48] 이 옳았다»를 훨씬 센 증거로 확인했습니다

지난번 판정 근거는 **「우리 토큰으로 물었더니 없다더라」** 였습니다. 그건 약한 증거입니다.
이번엔 **계정의 글을 «전부» 훑어서** 대조했습니다.

```
계정 nivs_poem (BUSINESS) · me/media 를 «끝까지» 넘겨 읽음 — 144건 (2쪽)
종류별 : CAROUSEL_ALBUM 108 · IMAGE 33 · VIDEO 3
가장 최근 글 : 2025-04-30      🔴 2026년 글이 «0건»
릴스(/reel/) : 3건 — 전부 2023년 것
```

**우리 기록 3건을 144건 «전부»와 대조:**

| 우리 id | id 로 찾기 | 저장된 주소로 찾기 |
|---|---|---|
| `17875798389564182` | ❌ 없음 | ❌ 없음 |
| `18129024544774483` | ❌ 없음 | ❌ 없음 |
| `18095011289101521` | ❌ 없음 | ❌ 없음 |

⚠ **「릴스라서 안 읽히는 것 아니냐」는 의심을 먼저 확인했습니다** — 아닙니다.
  계정에 **릴스가 3건 있고 그것들은 잘 읽힙니다**(2023년 것). **릴스라서가 아닙니다.**

⇒ 🔴 **우리 글 셋은 정말로 계정에 없습니다.** [48] 의 「지운 글을 맞게 잡는다」가 **옳습니다.**

⚠ **한 번 헛짚었습니다.** 처음엔 **첫 50건만** 대조하고 「없다」고 볼 뻔했는데,
  그 뒤 쪽에 릴스가 있었습니다. **끝까지 넘겨 읽고 나서** 결론을 냈습니다.

## 3. ✅ ♡·💬 숫자 — **같은 호출에서 함께 옵니다** (권반장님 ⑤)

```
me/media?fields=id,permalink,like_count,comments_count,media_type,timestamp
→ id=18010674922752674  ♡121 💬1   2023-07-23  .../reel/CvCvEBKtQ_i/
   id=18076077070351811 ♡158 💬2   2023-07-08
   id=17906459915719176 ♡82  💬0   2023-06-25
```

**두 번 부를 이유가 없다**는 권반장님 말씀이 맞습니다. **한 번에 다 옵니다.**

## 4. 🔴🔴 그런데 — **지금 손님 화면에 «죽은 링크» 2개가 걸려 있습니다**

published 인스타 3건 중 **2건은 «지워짐» 표시가 «안» 돼 있습니다**(주소도 살아 있습니다).
그런데 §2 에서 보듯 **그 글들은 계정에 없습니다.**

`lib/shorts.ts` 는 `remote_deleted_at IS NULL` 인 것을 보여 주므로 —
🔴 **손님이 「인스타에서 보기」를 누르면 «없는 글»로 갑니다.**

- 크론이 잡아 줍니다 — 다만 `RECHECK_AFTER_DAYS(7)` 이라 **09-23 · 09-24 쯤**입니다
- **제가 임의로 지움 표시를 하지 않았습니다.** 그것은 손님 화면에서 링크를 감추는 일이고,
  [48]① 에서 **「이 창구는 감추지 않는다」**로 정한 선을 제가 먼저 넘을 수 없습니다

## 5. 🔴 남은 일 — **숫자를 저장하려면 «DB 칸»이 필요합니다**

숫자는 가져올 수 있는데 **둘 자리가 없습니다.** `sns_posts` 에 jsonb 칸도 없습니다.

⇒ **`like_count` · `comments_count` 칸을 새로 만들어야 합니다.**
🔴 **DB 변경은 「권반장이 시킬 수 없는 것」 목록에 있습니다.** **대표님께 여쭙고 진행합니다.**

⚠ **저장 안 하고 «그때그때» 부르는 길도 있습니다.** 손님 화면은 ISR(60초)이라
  **사이트마다 1분에 한 번**만 부르게 됩니다 — 생각보다 적습니다.
  다만 **인스타가 느리면 홈페이지 만드는 것도 같이 느려집니다.** 저장하는 쪽이 낫다고 봅니다.

## 7. 다음에 제안드리는 것

목록 호출 자체가 실패하면 **「모른다」**로 남길 수 있어, **토큰 문제와 삭제를 가를 수 있습니다.**
🔴 다만 **비공개·보관(archive) 글이 목록에 나오는지는 여전히 안 해 봤습니다** — 그 시험이 먼저입니다.
