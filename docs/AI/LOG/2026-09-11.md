## ★★ 그래서 근본을 바꿨습니다 — 전환이 «필요 없게»

**카메라를 켜기 «전»에 어느 쪽으로 찍을지 먼저 여쭙습니다.**


## 17:05 · 카메라 전환 근본 재수정 (독점 접근 폰)

끝까지 팠습니다. **원인이 W3C 규격 문서로 확정됐고, 회장님 통찰 세 개가 전부 맞았습니다.**

## 원인 — 「카메라를 한 대만 열 수 있는 폰」

W3C 규격에 이렇게 적혀 있습니다: **「브라우저는 한 세션에 카메라 독점 접근을 요구할 수 있다.」** 안드로이드 폰 다수가 앞·뒤 카메라를 **동시에 못 엽니다.**

그래서 제 옛 코드(옛 것을 켠 채 새 것 열기)는:

| 회장님이 보신 것 | 코드에서 벌어진 일 |
|---|---|
| ③ [허용] → **검은 화면** | 새 카메라를 여는 순간 브라우저가 옛 것을 강제로 끊음 |
| ⑤ 두 번째 허용 뒤 **바뀌기 전 카메라** | deviceId 열기가 실패 → 코드가 «되살리기(원래 카메라)»로 떨어짐 |
| ⑥ 2~3번 반복해야 됨 | 매 누름이 한 번의 시도라, OS가 카메라를 풀 때까지 사람이 계속 누른 것 |

**회장님 지적이 세 개 다 정확했습니다:**
- 「새 것을 여는 게 옛 것을 죽인다」 → 맞습니다. 독점 접근 폰이라 그렇습니다.
- 「되살리기는 되는데 전환은 안 된다」 → 맞습니다. deviceId는 깨지고 facingMode만 됩니다.
- 「먼저 놓고, 기다린 뒤, 새 것을 열어라」 → 그게 정답이었습니다.

## 고친 것 — 순서를 뒤집었습니다

```
① 옛 카메라를 먼저 완전히 놓는다
② OS가 카메라를 풀 시간을 준다 (200 → 450 → 900ms, 점점 길게)
③ facingMode로 반대쪽을 연다 (deviceId 안 씀 — 그게 깨진 경로였음)
```

★ **재시도를 «한 번의 누름 안에서»** 합니다. 릴리스가 느린 폰이라도 사장님이 **여러 번 안 눌러도** 됩니다. 안에서 최대 세 번 시도하고, 그동안 「바꾸는 중…」이 떠 있습니다.

★ **영상만 요청**합니다. 마이크는 쓰던 것을 그대로 들고 가서, 팝업이 「카메라·마이크」로 뜨던 문제가 사라집니다.

## ★ 제일 신경 쓴 것 세 가지

**1. 토큰이 손님 브라우저에 못 가게 — «말»이 아니라 «타입»으로 막았습니다**

`Connection` 타입에 **토큰 칸이 아예 없습니다.** 화면도 API 응답도 이 타입만 씁니다. 실수로도 실을 수 없습니다. 토큰은 `lib/sns/db.ts` 의 `readTokens()` 한 곳에서만 꺼냅니다.

**2. 같은 영상이 두 번 올라가지 않게 — 세 겹**

| 겹 | 무엇 |
|---|---|
| DB | 「살아 있는 시도」에만 걸리는 유일 인덱스 — 경쟁 상황에서도 두 줄이 안 생김 |
| 코드 | `isDuplicate()` 를 시작 전에 확인 |
| ★ 핵심 | `container_id` — ②에서 끊겨도 **①을 다시 하지 않음** |

★ 그리고 **서버가 5분을 기다리지 않습니다.** 서버리스가 5분을 붙들면 시간 초과로 끊기는데, **그 끊김이 곧 두 번 올리기의 원인**입니다. 서버는 「지금 됐나」만 보고 즉시 답하고, 화면이 1분 간격으로 최대 5번 이어 갑니다.

**3. 조용히 실패하지 않게**

- 못 쓰는 SNS 는 **왜 못 쓰는지**를 그 자리에 씁니다 (「유튜브는 아직 준비 중이에요」)
- 못 쓰는 것은 **체크가 아예 안 눌립니다**
- 오류는 네 값뿐 — **모르는 것은 전부 TRANSIENT**. 「모르니까 거절」로 단정하면 다시 하면 될 일을 영영 포기하게 만듭니다
- 영상 규격은 **파일을 직접 열어** 잽니다(크기·가로폭·moov 위치). ⚠ **못 잰 것은 막지 않습니다** — 모른다고 멀쩡한 영상을 버리면 안 됩니다
