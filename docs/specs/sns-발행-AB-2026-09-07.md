## ★ 0. 이번 조사에서 나온 것 중 제일 중요한 여섯

### ⓐ 회장님이 못 찾으신 「비즈니스 인증」 메뉴 — 위치가 다르다

> **「앱 대시보드에서 앱을 읽어들이고 `설정 > 기본 > 인증`에서 **[인증 시작]** 버튼을 클릭」**
> — 개발자 문서 「비즈니스 인증」

**`business.facebook.com` 이 아니라 「앱 대시보드」다.** 그리고 **앱이 있어야 나온다.**
지금 앱이 0개라 그 메뉴가 없는 것이 정상이다. **앱 만들기가 먼저다.**

### ⓑ A 방식은 비즈니스 인증이 **필요 없다**

> 「앱이 앱 자체에서 **역할이 부여된 앱 사용자만** 사용할 경우 인증을 완료할 필요가 없습니다.
> 해당 사용자는 언제든 앱에 아무 권한이나 부여할 수 있고 **모든 기능이 항상 활성화**됩니다.」

→ **우리 계정 `@nivs_poem` 에만 발행하는 A 는 심사도 인증도 없이 지금 바로 된다.**

### ⓒ B 방식은 비즈니스 인증이 **반드시** 필요하다

> 「고급 액세스 권한을 요청하는 앱과 **다른 비즈니스가 앱 데이터에 액세스하도록 허용하는 앱**은
> 비즈니스 인증을 완료한 비즈니스에 연결되어야 합니다. **그때까지는 비즈니스의 앱 사용자가
> 앱에 권한을 부여할 수 없고 모든 기능이 비활성화됩니다.**」

→ 사장님 계정에 대신 발행 = 정확히 이 경우. **인증 없이는 사장님이 권한을 줄 수조차 없다.**

### ⓓ ⚠ 우리 문서가 두 갈래를 섞어 놨다 — 지금 바로잡아야 한다

Instagram 발행 API 는 **완전히 다른 두 갈래**가 있다:

| | **Instagram 로그인** 갈래 | **Facebook 로그인** 갈래 |
|---|---|---|
| 호스트 | `graph.instagram.com` | `graph.facebook.com` |
| 토큰 | Instagram 사용자 액세스 토큰 | **Facebook 페이지** 액세스 토큰 |
| 권한 | `instagram_business_basic`<br>`instagram_business_content_publish` | `instagram_basic`<br>`instagram_content_publish`<br>`pages_read_engagement` |
| 로그인 | Instagram용 비즈니스 로그인 | 비즈니스용 Facebook 로그인 |

**우리가 문서에 적어온 권한 2개는 「Instagram 로그인」 갈래**인데,
**토큰 조회 계획(`GET /{page-id}?fields=instagram_business_account`)은 「Facebook 로그인」 갈래**다.
**섞여 있다.** 어느 갈래로 갈지 먼저 정해야 한다 (§3).

### ⓔ ⚠ **인스타는 JPEG 만 받는다**

> 「유일하게 지원되는 이미지 형식은 **JPEG** 입니다.」

우리 저장소는 WebP(그리고 (라) 뒤에는 AVIF)다.
→ **발행 파이프라인에 「JPEG 로 내보내기」 단계가 반드시 필요하다.** 새 요구사항이다.
(라) 계획과 충돌하지는 않는다 — 저장은 AVIF/WebP, **발행용만 JPEG 사본**을 만든다.

### ⓕ 미디어는 **공개 주소**에 있어야 한다 (또 확증됐다)

> 「Facebook에서는 게시 시도 시 사용한 미디어에 대해 **cURL을 실행**해야 하므로
> **공개적으로 액세스 가능한 서버에서 호스팅**해야 합니다.」

[L] 조사의 「공개 버킷」 결론이 **세 번째로** 확증됐다.

## 1. 사용 제한 (하루 발행 한도)

> 「Instagram 계정은 **24시간 이내에 API를 통해 게시물을 최대 100개**까지 게시할 수 있습니다.
> 슬라이드는 단일 게시물로 간주됩니다.」

⚠ **같은 문서의 슬라이드 절에는 「최대 50개」로 적혀 있다.** 문서 안에서 값이 다르다.
→ **안전하게 50 으로 잡고 설계한다.** 실제 잔량은 API 로 물어볼 수 있다:
`GET /<IG_ID>/content_publishing_limit`

**사장님 1인당 하루 1편이면 50명분.** 초기에는 넉넉하다. B 로 가면 계정마다 별도 한도라 더 여유롭다.

### 새로 나온 관문 — PPA(페이지 게시 인증)

> 「페이지 게시 인증(PPA)이 필요한 페이지에 연결된 Instagram 프로페셔널 계정에는
> **PPA를 완료할 때까지 게시할 수 없습니다.** … 앱 사용자에게 **미리 PPA를 완료하도록
> 안내하는 것이 좋습니다.**」

→ B 단계에서 **사장님 온보딩에 「PPA 먼저 해주세요」 안내가 필요**하다. 미리 알아 둘 것.

## 3. ★ 먼저 정할 것 — 어느 갈래로 가는가 (ⓓ)

이걸 정해야 코드도 토큰 조회도 방향이 선다.

| | Instagram 로그인 갈래 | Facebook 로그인 갈래 |
|---|---|---|
| 사장님이 겪는 것 | **인스타 계정으로 바로 로그인** | 페이스북 로그인 → 페이지 선택 → 인스타 선택 |
| 사장님 준비물 | 인스타 프로페셔널 계정 | 프로페셔널 계정 **+ 페이스북 페이지 + 둘의 연결** |
| 우리 쪽 복잡도 | 낮다 | 높다(페이지 토큰·PPA·ads 권한까지) |
| 지금 상태와 맞나 | 우리가 적어온 권한 2개가 이쪽 | 우리 토큰 조회 계획이 이쪽 |

### 제 의견: **Instagram 로그인 갈래가 맞다**

이유는 하나다 — **사장님이 페이스북 페이지를 만들 수 있느냐**다.
회장님도 페이지 만들고 인스타 연결하는 데 여러 번 실패하셨다. **그걸 소상공인 사장님에게
요구하면 온보딩이 거기서 끊긴다.** 인스타 계정만으로 되는 쪽이 우리 제품과 맞는다.

⚠ **다만 확정은 미룬다.** 지금 고른 이용 사례(「Instagram에서 메시지 및 콘텐츠 관리」)가
어느 갈래를 여는지 **앱을 만든 뒤 대시보드에서 실제로 확인**해야 한다. 추측하지 않는다.

### 그래서 토큰 조회 계획도 바뀐다

- Facebook 로그인 갈래라면 → `GET /1328742146980908?fields=instagram_business_account`
- **Instagram 로그인 갈래라면** → 페이지를 거치지 않는다. `graph.instagram.com/me` 로
  Instagram 사용자 토큰을 확인한다

**앱을 만든 직후 어느 쪽인지 보고, 맞는 조회를 실행해서 보고하겠다.**

⚠ **이 절은 아직 불완전하다.** 「비즈니스 인증에 필요한 문서 리스트」는 Meta 가
**비즈니스 관리자 고객 센터** 쪽 문서로 넘겨 두었고, 이번 배치에서 거기까지 못 갔다.
**아래는 확인된 것만 적는다. 추측으로 채우지 않는다.**

| 서류 | 우리에게 있나 | 비고 |
|---|---|---|
| **사업자등록증** | ✅ 있다 | `etc/사업자등록증.pdf` — 검사 완료, 제출 가능 판정 |
| **개인정보처리방침 URL** | ✅ 있다 | `/privacy` (앱 설정에 넣어야 한다) |
| **이용약관 URL** | ✅ 있다 | `/terms` |
| 요금납부 내역서 / 지방세 납세증명 | — | 사업자등록증 대신 쓸 수 있는 대체 서류 |
| 「보안 문서」·「데이터 보관 정책」 | ❓ **미확인** | **다음 배치에서 조사** |

⚠ **회장님 지시대로, 우리가 실제로 하지 않는 것은 문서에 적지 않는다.**
데이터 보관 정책 초안을 쓸 때는 `lib/trial.ts` 의 실제 정책(30일 무료 → 정지 → 정지 후 60일 파기)과
불변 규칙 10(삭제는 표시 변경)을 **그대로** 옮긴다. 문서용으로 새 약속을 만들지 않는다.

### 유료 여부

확인한 문서 범위에서 **비즈니스 인증·앱 심사에 요금 언급은 없다.** 무료로 보인다.
⚠ 다만 「없다고 확인」한 것이 아니라 「언급을 못 봤다」이므로 **판정 보류**로 둔다.

## 5. ★ 코드 구조 — A→B 를 설정 한 곳으로 (회장님 [3]4)

핵심은 **「누구 계정에 올리는가」를 코드에서 뽑아내는 것**이다.

```
lib/social/
  targets.ts   ← ★ 여기만 바뀐다. 발행 대상을 고르는 유일한 곳
  instagram.ts ← 컨테이너 만들기 → 업로드 → media_publish (대상은 인자로 받는다)
  threads.ts
  media.ts     ← 발행용 JPEG 사본 만들기 (ⓔ)
```

`targets.ts` 가 하는 일은 하나다 — **사이트 하나를 받아 「어디에 올릴지」를 돌려준다.**

```ts
// A: 무엇을 받든 온스토리 계정 하나를 돌려준다
// B: 사이트에 연결된 사장님 계정을 돌려준다
export async function resolveTarget(slug: string): Promise<PublishTarget>
```

`PublishTarget` = `{ igUserId, accessToken, kind: "onstori" | "owner" }`

**나머지 코드는 `resolveTarget` 이 무엇을 주는지 모른다.** A→B 전환은
이 함수 하나를 바꾸는 일이 된다. 호출부는 한 줄도 안 바뀐다.

### 지금부터 지킬 것 3가지

1. **토큰을 전역 상수로 읽지 마라.** `process.env.IG_TOKEN` 을 `instagram.ts` 안에서
   직접 읽으면 그 순간 A 에 못 박힌다. **토큰은 항상 `PublishTarget` 을 통해 들어온다.**
2. **DB 에 자리를 미리 비워 둔다.** 사장님 계정 연결 정보가 들어갈 곳
   (`sites.settings.social` 같은 jsonb 한 칸). **지금은 비어 있고, A 에서는 안 읽는다.**
   jsonb 라 마이그레이션이 필요 없다.
3. **발행 기록을 남긴다.** 언제·어디에·무엇을 올렸는지. A 에서 쌓인 이 기록이
   **B 심사의 「실제 작동 증빙」이 된다**(회장님 말씀대로 버리는 작업이 아니다).

### A→B 에서 버려지는 것 — **거의 없다**

| | A 에서 만든 것 | B 에서 |
|---|---|---|
| 컨테이너→업로드→발행 흐름 | 그대로 | ✅ 재사용 |
| JPEG 변환 · 공개 버킷 | 그대로 | ✅ 재사용 |
| 발행 기록·재시도·한도 처리 | 그대로 | ✅ 재사용 |
| `resolveTarget` | 온스토리 고정 | 🔄 **여기만 교체** |
| **사장님 계정 연결 UI(OAuth)** | 없다 | ➕ **새로 만든다** |

**버려지는 것은 없고, B 에서 「사장님이 자기 인스타를 연결하는 화면」 하나가 늘어난다.**
그 화면은 A 에서는 만들 이유가 없으니 낭비가 아니다.

### 이용 사례 — 3개로 늘렸다 (회장님 지시: 「제대로 신청해라」)

| # | 이용 사례 | 무엇이 열리나 |
|---|---|---|
| 1 | **Instagram에서 메시지 및 콘텐츠 관리** | 피드·**릴스**·스토리 게시, 댓글, DM |
| 2 | **Threads API 액세스** | 쓰레드 게시·답글 |
| 3 | **페이지의 모든 부분 관리** ← 새로 추가 | **페이스북 페이지 게시**, 댓글·인사이트 |

★ **릴스는 별도 신청이 아니다.** 1번 안에 들어 있다 — 같은 `/media` 엔드포인트에
`media_type=REELS` 를 주면 된다(공식 문서 확인). 스토리도 `media_type=STORIES` 로 같은 자리다.
**따로 신청할 것이 없었다.**

### ★ 「기술 제공업체 되기」 진입점을 찾았다 — B 의 문이다

앱 대시보드에 이 항목이 있다:

> **「기술 제공업체 되기」** — 기술 제공업체가 되어 앱 검수를 제출하고
> **다른 비즈니스의 사용자 데이터 및 기타 데이터에 대한 액세스를 요청**하세요.
> **액세스 인증을 완료해야 합니다.**

= B(사장님 계정에 대신 발행)의 정식 경로. **위치: 앱 대시보드 첫 화면 아래쪽.**
`business.facebook.com` 이 아니다. 회장님이 헤매신 이유가 이것이다.

## 9. ⚠ 페이스북 페이지를 추가하면서 생긴 판단 지점

§3 에서 「Instagram 로그인 갈래가 맞다」고 적었는데, **페북 페이지 게시를 넣으면 달라진다.**

- 페이스북 페이지에 글을 올리려면 **페이지 액세스 토큰**이 필요하고, 그건 **Facebook 로그인**으로만 나온다
- 즉 **인스타 + 페북을 둘 다 하려면 결국 Facebook 로그인 갈래**로 가게 된다
- 그러면 **사장님도 페이스북 페이지를 만들어야 한다** — 회장님도 여러 번 실패하신 그 과정이다

### 두 갈래 중 선택 (B 단계에서 결정하면 된다)

| | ㉮ 인스타·쓰레드만 (Instagram 로그인) | ㉯ 인스타·쓰레드·페북 (Facebook 로그인) |
|---|---|---|
| 사장님 준비물 | 인스타 프로페셔널 계정 하나 | 인스타 + **페북 페이지 + 연결** |
| 온보딩 이탈 | 낮다 | **높다** |
| 채널 수 | 2 | 3 |

**A(우리 계정)에서는 문제가 안 된다** — 우리는 이미 페이지·인스타·연결이 다 있다.
**문제는 B 다.** 사장님께 페이지까지 만들라고 할 것인가.

⚠ **지금 정하지 않아도 된다.** 이용 사례는 3개 다 켜 뒀으니 **둘 다 가능한 상태**다.
A 를 돌려 보고, 사장님들이 실제로 어디서 막히는지 본 뒤 B 설계에서 정하는 것이 맞다.
§5 의 `resolveTarget` 구조가 이 선택도 흡수한다 — `PublishTarget` 에 채널별 대상이 들어가면 된다.
