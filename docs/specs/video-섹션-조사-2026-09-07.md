## 1. `/rec` 로 올라간 영상을 손님 사이트에서 재생하려면 — **공개 버킷이 답이다**

### 지금 어디에 있나

`app/api/story/upload-url/route.ts` 가 발급하는 키는

```
private/stories/{slug}/{uuid}.webm     ← 비공개 버킷
```

같은 파일 주석이 이미 답을 적어 두었다: **「발행본(자막 영상)은 워커가 media 버킷으로 낸다」.**
즉 설계상 이미 공개 버킷 복사 쪽으로 정해져 있었다. 아래는 그게 맞다는 확인이다.

### 두 방식 비교

| | **(A) 공개 버킷 복사** | (B) 서명 GET URL |
|---|---|---|
| 손님 사이트 캐시 | ✅ 그대로 산다 | ❌ **깨진다** (아래) |
| CDN | ✅ R2 `immutable` 1년 · 전송 무료 | ❌ 매번 새 URL이라 캐시 못 함 |
| 서버 부담 | 0 (정적 HTML에 주소만 박힌다) | 조회마다 서명 발급 |
| 주소 노출 | UUID 공개 주소 (추측 불가하지만 영구) | 10분 뒤 만료 |
| 규칙 10 (삭제=표시 변경) | ✅ 그대로 적용 | ✅ |

### ★ (B)를 쓰면 안 되는 진짜 이유

손님 사이트는 **ISR `revalidate 60` + `generateStaticParams` 로 미리 만들어 둔 정적 페이지**다
(2026-09-07 3차에서 `/[slug]` 를 `● 1m` 으로 바꿔 TTFB 를 12배 줄인 그것).

서명 URL 은 **10분짜리 주소를 HTML 안에 구워 넣는다.** 그 HTML 은 60초~빌드 시점부터 살아 있으므로
**손님이 10분 뒤에 들어오면 영상이 재생되지 않는다.** 이걸 피하려면 둘 중 하나인데 둘 다 나쁘다:

- 페이지를 `force-dynamic` 으로 되돌린다 → **3차 배치에서 얻은 TTFB 0.075초를 반납한다**
- 손님 브라우저가 재생 직전에 서명 URL 을 받아 오게 한다 → 왕복 1회 추가 + JS 필요

**결론: (A) 공개 버킷 복사.** 어차피 사장님이 자기 홈페이지에 걸려고 찍은 영상이다 — 비공개일 이유가 없다.
원본(`private/`)은 그대로 두고 **발행본만** `media/` 로 낸다. 원본 = 증거, 발행본 = 공개물로 갈린다.

### 예상 시간

| 일 | 시간 |
|---|---|
| 워커가 `media/stories/{slug}/{uuid}.mp4` 로 내보내고 `video_out_key` 에 기록 | STEP 4 자막 워커에 이미 포함 |
| 자막 없이 원본만 먼저 걸 경우의 복사 단계 (선택) | 0.5h |
| 섹션 렌더러 + `<video>` 플레이어 (표지·재생·자막 트랙) | 2.0h |
| 에디터 폼 (영상 고르기·설명·순서) | 1.5h |
| **합계** | **약 3.5~4h** (자막 워커 제외) |

## 2. 표지 사진(첫 프레임)을 브라우저 canvas 로 뽑을 수 있나 — **된다. 단 「녹화 직후」에 뽑아야 한다**

### 된다

`<video>` → `canvas.drawImage(video, 0, 0)` → `canvas.toBlob()`. 새 라이브러리가 필요 없다.
같은 방식이 이미 저장소에 있다 — `components/sections/quote-form.tsx:47` 이 손님 사진을
canvas 로 1600px·JPEG 0.8 까지 줄여서 올린다. **검증된 경로다.**

### ⚠ 반드시 녹화 직후에 뽑아라 (나중에 뽑으면 막힌다)

| 언제 | 영상 주소 | canvas 결과 |
|---|---|---|
| **녹화 직후 (`/rec`)** | `blob:` (MediaRecorder 결과, 같은 출처) | ✅ 깨끗하다. 바로 `toBlob()` |
| 나중에 (손님 사이트·에디터) | `https://img.onstori.com/...` (다른 출처) | ❌ **canvas 가 오염돼 `toBlob()` 이 SecurityError** |

나중에 뽑으려면 R2 에 CORS 를 열고 `<video crossOrigin="anonymous">` 를 붙여야 한다.
설정이 늘고 실패 지점이 는다. **녹화 화면(`app/rec/[slug]/rec-client.tsx`)에서 뽑는 게 맞다** —
거기엔 이미 `blobUrl` 로 미리보기를 띄우는 `<video>` 가 있다(317행). 그 요소를 그대로 쓰면 된다.

### 실무 주의 3가지

1. **0초를 찍지 마라.** webm/mp4 첫 프레임은 검은 화면인 경우가 많다.
   `video.currentTime = 0.8` 로 옮기고 `seeked` 를 기다린 뒤 찍는다.
2. **iOS 사파리** 는 `playsInline` + `muted` 가 있어야 프레임이 그려진다.
   두 속성은 이미 붙어 있다(rec-client.tsx 317행).
3. **실패해도 막지 마라.** 표지가 없으면 `<video poster>` 없이 나갈 뿐이다.
   업로드를 막으면 60초 녹화가 통째로 날아간다.

예상 0.8h.

## 3. 영상 여러 편의 순서·설명 저장 — **`story_entries` 확장이 낫다. 새 표를 만들지 마라**

### 지금 `story_entries` 에 이미 있는 것

`20260831120000_core.sql` + `20260905090000_mainplan_membership.sql`

| 칸 | 쓰임 |
|---|---|
| `title` | 영상 제목 ✅ |
| `body` | **설명 ✅ (이미 있다)** |
| `question` · `transcript` | 녹화 질문 · 받아쓴 글 |
| `video_key` · `video_out_key` | 원본 · 발행본 ✅ |
| `media_status` | none→uploaded→processing→ready→failed ✅ |
| `visible` | 삭제 대신 숨김 (규칙 10) ✅ |
| `entry_date` | 지금 정렬 기준 (`story_entries_site_idx` = site_id, entry_date desc) |

**한 줄 = 한 편**이다. 설명도 이미 있다. 진짜로 없는 건 **명시적 순서** 하나뿐이다.

### 왜 새 표가 아닌가

1. **1:N 이 아니다.** 새 표는 「이야기 하나에 영상 여러 편」일 때 값을 한다.
   기획1은 **60초 한 편 = 이야기 한 편**이다. 지금 구조가 이미 맞다.
2. **새 표를 만들면 세 곳을 복제해야 한다** — RLS 정책 2개(`stories_public_read`·`stories_owner_all`),
   완성도 점수(`config/completeness.ts`), 실적 카운터(`workCount`). 전부 `story_entries` 를 보고 있다.
3. **렌더링마다 join 이 붙는다.** 손님 사이트는 정적 생성이라 join 이 빌드 시간을 그대로 늘린다.
4. 마이그레이션 크기가 다르다 — `add column sort` 한 줄 vs `create table` + RLS 2개 + 인덱스.
   되돌리기도 전자가 훨씬 쉽다.

### 필요한 마이그레이션 (⚠ 회장님 승인 필요 — 스키마 변경)

```sql
alter table story_entries
  add column if not exists sort int not null default 0;
-- 0 이면 지금처럼 entry_date desc 로 떨어진다. 기존 줄은 손대지 않는다.
create index if not exists story_entries_order_idx
  on story_entries (site_id, sort, entry_date desc);
```

정렬은 `order by sort asc, entry_date desc`. **기존 데이터는 전부 `sort=0` 이라 지금 순서 그대로다.**
되돌리려면 컬럼을 안 읽으면 그만이다.

## 4. 히어로 다음에 영상 섹션을 넣으려면 — **`SectionGate` 는 관계없다**

### ★ 먼저 바로잡을 것

`SectionGate` 는 **본사 첫 페이지(`app/page.tsx`) 전용**이다.
`components/site/section-gate.tsx` 가 읽는 건 `lib/page-sections.ts` 의 `SectionId` —
`inside · portfolio · channels · pricing · faq` 다섯 개뿐이고, DB 표 `page_sections` 를 본다.

**손님 사이트(`app/[slug]`)는 이 장치를 아예 안 쓴다.** 손님 사이트는 자기 문서(`doc.sections`)
**배열 순서 그대로** 그린다. 그래서 "히어로 다음"은 곧 **배열의 2번째 자리**라는 뜻이고,
켜고 끄기는 사장님이 에디터에서 섹션을 넣고 빼는 것으로 이미 된다. 새 게이트를 만들 필요가 없다.

### 고칠 파일 — 불변 규칙 2 에 따라 **한 커밋에 4곳**

| # | 파일 | 무엇을 |
|---|---|---|
| 1 | `lib/schema.ts` | `Video` zod 스키마 추가(`type:"video"` · `videoUrl` · `poster` · `caption`) + `Section` union 에 넣기 |
| 2 | `components/sections/index.tsx` | 렌더러 `VideoSec` 추가 + 하단 switch 에 연결 |
| 3 | `app/[slug]/edit/ui.tsx` | 에디터 폼 (영상 고르기·설명·순서) |
| 4 | `docs/SCHEMA.md` | 문서 |

**같이 봐야 하는 곳 2개** (규칙 2의 4곳은 아니지만 안 하면 새 사이트에 안 들어간다):

- `lib/generate.ts` — 템플릿이 섹션 배열을 조립한다. **여기서 `hero` 바로 뒤에 꽂는다.**
- `lib/section-defaults.ts` — 「섹션 추가」로 넣을 때의 기본값

### ⚠ 기존 사이트는 저절로 안 생긴다

이미 발행된 사이트의 `doc.sections` 에는 영상 섹션이 없다. 둘 중 하나다:

- 사장님이 에디터에서 직접 추가 (권장 — 규칙 10 정신에 맞고 되돌릴 게 없다)
- 백필 스크립트로 일괄 삽입 (사장님 문서를 우리가 고치는 것이라 승인 필요)

### ⚠ 배경색 번갈아 규칙

디자인 v5 는 「흰·연회색·어두운을 번갈아 쓰고 같은 배경을 연속으로 두지 않는다」(규칙 11).
히어로 다음에 섹션을 하나 끼우면 **그 아래 전부가 한 칸씩 밀린다.**
`docs/specs/section-order.md` §3 이 같은 걸림돌을 이미 적어 두었다. 영상 섹션은 어두운 배경이 어울리므로
히어로(사진) → 영상(어두움) → 그다음(흰) 으로 두면 규칙을 지킨다.
