## 2. ★ [0-3] 회장님 이해가 **정확합니다** — 문서로 확인

Vercel 공식 문서(`/docs/deployment-storage`) 원문:

> Vercel 은 Deployment Storage 와 Functions Storage 를 **GB-월**로 잰다.
> 각 항목마다 **프로젝트별로 그날 저장된 최대량을 매일 기록하고**,
> 그 일별 값을 **청구 기간 내내 더한다.**

그리고 `/docs/deployment-retention` 원문:

> 보관 기간이 끝난 배포본은 **복구 기간(recovery period)** 에 들어간다.
> 이때 접속하면 410 이 나오지만, **복구 기간 동안 복원할 수 있다.**
> 성공한 배포본의 복구 기간은 **30일**이다. 30일이 지나야 관련 자원이 영구 삭제된다.
> …보관된 배포본 출력물은 **Vercel 이 저장하고 있는 동안 Deployment Storage 에 계속 포함된다.**

**따라서 두 가지 다 맞습니다:**

1. ✅ 보관 기간이 끝나도 **30일 복구 기간** 동안 자원이 남아 있고, **그동안 계속 용량으로 셉니다.**
2. ✅ 사용량은 **일별 값을 더한 GB-월 누적**이라 **이번 주기 숫자는 내려가지 않습니다.**

> **정확한 답은 「며칠 뒤 풀린다」가 아니라 「다음 청구 주기에 초기화된다」입니다.**
> 그리고 그 초기화는 **오늘(9월 7일) 이미 일어난 것으로 보입니다.**

## 3. [0-4] 지금 당장 비울 수 있나 — **사실상 없습니다**

수동으로 지워도 **성공한 배포본은 30일 복구 기간에 들어가고 그동안 자원이 남습니다.**
즉 **오늘 지워도 오늘 용량이 줄지 않습니다.**

게다가 Vercel 은 보관 정책과 무관하게 아래를 **항상 남깁니다**:

- 프로젝트의 **마지막 10개** 배포본
- 성공 상태 **프로덕션 마지막 20개**
- 성공 상태 **비프로덕션 마지막 20개**
- 프로덕션 주소가 걸린 배포본
- 활성 브랜치의 최신 미리보기

즉 **최소 40개 안팎은 무조건 남습니다.** 수동 삭제로 얻을 게 거의 없습니다.

## 4. ★ [0-5] 배포본 하나가 왜 큰가 — **진짜 원인을 찾았습니다**

`next.config.ts` 가 이렇게 돼 있었습니다:

```ts
outputFileTracingIncludes: {
  "/api/**": [                                    // ← ★ API 라우트 전부
    "./node_modules/@img/sharp-linux-x64/**",
    "./node_modules/@img/sharp-libvips-linux-x64/**",
  ],
}
```

`sharp` 는 사진을 줄이는 도구이고, 리눅스용 파일에는 **libvips 라는 큰 이미지 라이브러리**가
통째로 들어 있습니다. 이걸 **API 라우트 30개 전부**에 밀어 넣고 있었습니다.

**그런데 sharp 를 실제로 쓰는 라우트는 5개뿐입니다:**

| 라우트 | 왜 필요한가 |
|---|---|
| `/api/inquiry` | 손님이 올린 사진 줄이기 |
| `/api/site/logo` | 로고 줄이기 |
| `/api/site/upload` | 사장님 사진 줄이기 |
| `/api/site/publish` | `lib/site-shot.ts` 경유 |
| `/api/admin/site-shot` | `lib/site-shot.ts` 경유 |

**나머지 25곳은 쓰지도 않는데 배포본마다 사본이 붙었습니다.**

### 고친 것

```ts
const SHARP_LINUX = [ ... ];
outputFileTracingIncludes: {
  "/api/inquiry": SHARP_LINUX,
  "/api/site/logo": SHARP_LINUX,
  "/api/site/upload": SHARP_LINUX,
  "/api/site/publish": SHARP_LINUX,
  "/api/admin/site-shot": SHARP_LINUX,
}
```

⚠ 여기서 한 곳이라도 빠지면 그 라우트가 프로덕션에서 500 이 납니다
(`ERR_DLOPEN_FAILED: libvips-cpp.so.8.18.6`). 새로 sharp 를 쓰는 라우트를 만들면
**반드시 이 목록에 줄을 추가해야 합니다.**

### 나머지 항목 실측 — 다 작습니다

| 항목 | 크기 | 판단 |
|---|---|---|
| `content/plandept` | 904 KB | 작다. 그대로 둔다 |
| `content/onstoriplandept` | 948 KB | 작다 (제일 큰 파일 `index.html` 945KB) |
| `content/mainplan` | 248 KB | 작다 |
| **content 합계** | **2.1 MB** | 회장님 걱정과 달리 문제가 아니다 |
| `public/` 전체 | 3.6 MB | — |
| └ 글꼴(Pretendard 92조각) | **3.1 MB** | 한글 전 영역 커버. 회장님 지시로 **더 줄이지 않는다** |

## 5. [0-3] 보관 기간 설정 검토 — **적절합니다**

회장님이 바꾸신 값 (API 로 확인, 실제 반영돼 있음):

| 상태 | 회장님 설정 | Hobby 기본값 | 의견 |
|---|---|---|---|
| Canceled | **1일** | 30일 | ✅ 좋다. 취소된 빌드는 볼 일이 없다 |
| Errored | **1일** | 30일 | ⚠ 살짝 짧다. **빌드가 실패한 로그를 다음 날 아침에 보려면 3일이 낫다.** 다만 로그는 따로 남으므로 1일이어도 큰 문제는 아니다 |
| Pre-Production(미리보기) | **1주** | 30일 | ✅ 좋다 |
| Production | **30일** | 30일 | ✅ 좋다 |
| (같이 걸려 있음) 최소 보관 개수 | 10개 | 10개 | 건드릴 수 없다 |

**「되돌리기는 git 태그로 하니 오래된 배포본은 필요 없다」는 판단에 동의합니다.**
다만 한 가지만 덧붙이면 — git 태그로 되돌리려면 **다시 빌드**해야 하고 몇 분이 걸립니다.
Vercel 의 즉시 되돌리기(Instant Rollback)는 **이미 빌드된 것을 바로 바꿔치기**해서 초 단위입니다.
프로덕션 30일은 그 안전장치를 30일치 남겨 두는 값이라 적절합니다. 더 줄이지 마시길 권합니다.

## 6. [0-6] 앞으로 — 배포 횟수를 줄인다

지시대로 하겠습니다: **한 배치를 다 끝내고 마지막에 한 번만 push.** 중간은 로컬 커밋.
⚠ 단 세션 한도가 가까워지면 작업을 잃지 않도록 그때는 push 합니다.

참고로 8/25 하루에 **94번** 배포됐습니다. 한 배치 = 1배포로 바꾸면
하루 3~5개 수준으로 떨어집니다. **이게 가장 큰 절감입니다** — 배포본 하나를 줄이는 것보다
배포본 개수를 줄이는 쪽이 훨씬 큽니다.

## 7. 회장님 결정이 필요한 것

1. **오류 배포본 4개 삭제** — 눌러도 되지만 효과는 거의 없습니다. 하실지 말지.
2. **Errored 보관 1일 → 3일** 로 올릴지. 빌드 실패를 다음 날 아침에 보시려면 3일이 낫습니다.
3. Pro 업그레이드는 **지금 필요 없습니다.** 배포가 막히지 않았고, 주기가 초기화됐으며,
   배포 횟수를 줄이면 다음 주기는 훨씬 여유롭습니다.
